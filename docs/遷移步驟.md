## 3. 步驟

### 3.1 凍結九個部門（一個 PR）

1. 群組公告：「看板 ○點起暫停編輯，請先存好、關掉所有看板分頁（包括手機）」。
2. 合併「凍結九個部門」的 PR。內容：`dept/config.js` 九個部門那一行最後加 `source: "frozen"`，水果部不動：
   ```js
   { id: "rights",      name: "權益部", path: "data.json", boardId: "board-main", logo: true, source: "frozen" },
   { id: "president",   name: "會長室", follow: true, grant: true, ext: "會長室", extIcon: "flag", mergeDone: true, source: "frozen" },
   { id: "secretariat", name: "秘書處", meeting: true, ext: "會議", extIcon: "calendar", mergeDone: true, source: "frozen" },
   { id: "marketing",   name: "行銷部", source: "frozen" },
   { id: "finance",     name: "財務部", source: "frozen" },
   { id: "events",      name: "活動部", source: "frozen" },
   { id: "affairs",     name: "社務部", source: "frozen" },
   { id: "pr",          name: "公關部", source: "frozen" },
   { id: "works",       name: "工務部", source: "frozen" },
   ```
3. 等 1～2 分鐘，九個網址各打開一次（`https://stustsa.github.io/council/index.html?d=代號`，權益部不加 `?d=`）：每個都看到「這個部門正在搬到新資料庫，暫停編輯。」＝凍結成功。

凍結只靠程式設定，不寫資料檔。**還開著舊版頁面的分頁仍然能存檔**（它載入的是凍結前的程式）：所以第 1 步要大家關分頁，第 3.4 節的核對與第 3.8 節的收尾核對會抓到漏網的。

### 3.2 記下來源版本（一個 commit＋九個 SHA-256）

凍結上線後，在你電腦的 repo 資料夾（或 Google Cloud Shell 先 `git clone https://github.com/STUSTSA/council.git && cd council`）：

```bash
mkdir -p ~/看板備份/切換前 && git fetch origin main && git rev-parse origin/main | tee ~/看板備份/切換前/commit.txt
```

```bash
for f in data.json data-president.json data-secretariat.json data-marketing.json data-finance.json data-events.json data-affairs.json data-pr.json data-works.json; do printf '%s  %s\n' "$(git show origin/main:$f | sha256sum | cut -d' ' -f1)" "$f"; done | tee ~/看板備份/切換前/SHA256.txt
```

- 第一個指令印出的 40 碼就是這次的 **commit**（九個部門共用同一個）；第二個印出九行「SHA-256  檔名」。兩個檔都存在 `~/看板備份/切換前/`。
- macOS 沒有 `sha256sum`：把 `sha256sum` 換成 `shasum -a 256`。
- （可選）在 repo 上留標籤：`git tag pre-firestore-all-日期 origin/main && git push origin pre-firestore-all-日期`（要你的電腦已經用自己的帳號登入 GitHub；沒有就跳過，commit 已經抄下來了）。

### 3.3 備份（九個資料檔）

```bash
for f in data.json data-president.json data-secretariat.json data-marketing.json data-finance.json data-events.json data-affairs.json data-pr.json data-works.json; do git show origin/main:$f > ~/看板備份/切換前/$f; done; ls -l ~/看板備份/切換前
```

這九份就是切換前的完整內容（含雲端設定、密碼雜湊、加密的權杖：**不要貼到群組**）。整個 `切換前` 資料夾存到學生會公用帳號雲端硬碟、只有幹部看得到的資料夾。

### 3.4 逐部門匯入

順序：秘書處 → 會長室 → 行銷部 → 財務部 → 公關部 → 工務部 → 社務部 → 活動部 → 權益部（學年設定與會長室的追蹤先進來；資料最多的權益部最後）。

每個部門：

1. 總管理員打開水果部或任何一個凍結中的部門 → 設定 →（還沒登入就用 Google 登入）→ 系統管理 →「匯入」。
2. 點那個部門（旁邊標「凍結中」；標「GitHub」＝凍結還沒上線，停下來回 3.1）。
3. 兩格：**commit**＝3.2 的 `commit.txt`（每個部門都一樣）；**SHA-256**＝`SHA256.txt` 裡那個部門的檔名那一行的 64 碼 → 確定。
4. 核對通過才會出現**確認畫面**（還沒寫入）。看：來源的檔名與 repo（`STUSTSA/council`）對、會寫入的筆數合理、**舊身分名單**跟 P5 的名單對得上；有「格式不合會清空的欄位」或「超過規則上限」→ 不要匯入，截圖回報（附錄 A.3 的 D 第 6～7 步有每種紅字的意思）。
5. 按「確認匯入」→ 報告：最上面是**正式專案 ID**（不是 `stustsa-council-dev`）、每一列「相同」、V1～V4、V6「通過」、「結果：通過」、衝突 0（沒有 V5 是正常的：V5＝重跑一次）。
6. 記在下面這張表（截圖報告也可以）：

| 部門 | commit 前 12 碼 | 確認畫面的舊身分人數 | 報告結果 | 衝突 |
|---|---|---|---|---|
| 秘書處 | | | | |
| 會長室 | | | | |
| 行銷部 | | | | |
| 財務部 | | | | |
| 公關部 | | | | |
| 工務部 | | | | |
| 社務部 | | | | |
| 活動部 | | | | |
| 權益部 | | | | |

- 報告裡「指到還沒匯入的部門 N 筆」是正常的（例如會長室追蹤了權益部，權益部還沒匯入）；全部匯完後在會長室按「再匯入一次」，那一行應該變成 0。
- 紅字「這個 commit 之後資料檔又被改過」＝凍結後有人用舊分頁存了檔：**這個部門重做 3.2（只重抄那一個檔的 SHA-256 與新的 commit）、3.3 那一個檔**，再匯入；其他部門不用重來。
- 任何一個部門失敗或報告不同：其他部門可以繼續匯入，但**不要做 3.5**，看第 4 節。

### 3.5 九個部門切成 firestore（一個 PR）

九個部門都「結果：通過」才做。合併「九個部門切成 firestore」的 PR：3.1 那九行的 `source: "frozen"` 全部改成 `source: "firestore"`。等 1～2 分鐘。

### 3.6 確認

1. 九個網址各打開一次：沒登入＝提示要登入；用 Google 登入後看得到卡片、議題、週報（拿 3.3 的備份對照幾張）。
2. 總管理員在權益部新增一張卡片 → 儲存 → 重新整理還在 → 設定 → 編輯紀錄有這一筆 → 刪掉它（D-1 的做法）。
3. 總覽頁（`home.html`）打開正常；會長室的追蹤、秘書處的「會議」分頁讀得到各部門。

### 3.7 部門的人加入（QR）

照附錄 A.3 的 F：總管理員 → 系統管理 →「QR 邀請」→ 選部門、角色、**舊身分**（P5 的表）→ 產生 → 那個人用手機相機掃 → Google 登入 →「加入」。QR 10 分鐘、一次性，人多就「重新產生」。最後在「人員」核對每個人的部門與角色。

還沒加入的人照樣看得到看板（唯讀），所以這一步可以慢慢做，不影響其他人。

### 3.8 收尾核對（作廢權杖之前）

1. **資料檔在凍結後沒有再被改過**（有的話＝有人用舊分頁存進 GitHub，那些修改不在新資料庫）：
   ```bash
   git fetch origin main && for f in data.json data-president.json data-secretariat.json data-marketing.json data-finance.json data-events.json data-affairs.json data-pr.json data-works.json; do printf '%s  %s\n' "$(git show origin/main:$f | sha256sum | cut -d' ' -f1)" "$f"; done | diff ~/看板備份/切換前/SHA256.txt - && echo 資料檔都沒變
   ```
   印出「資料檔都沒變」才往下。有差異：`git log origin/main --format="%h %ad %s" --date=iso -- 那個檔名` 看是哪一筆存檔、改了什麼（訊息就是「〔名字〕類別｜內容」），請那個部門在新資料庫的看板上補做那幾項修改；**不要改資料檔**。補完再往下。
2. 系統管理 →「匯出全部資料」，存到 3.3 同一個資料夾（含角色與信箱，只有幹部看得到）。
3. 每個部門至少一位編輯者已經加入、改過一次卡片成功。

### 3.9 作廢權杖（當天，由你本人在 GitHub 網頁操作）

1. GitHub → 右上頭像 → Settings → Developer settings → Personal access tokens →「Fine-grained tokens」→ 看板用的那一把 → 最下面「Delete」（或「Revoke」）。
2. 作廢後：網站照常；GitHub 模式的存檔路徑已經沒有部門在用（九個部門都是 firestore）。看板資料檔裡加密的權杖從此沒有作用。
3. 作廢後要退回 GitHub 寫入：只能照 T2 再發一把新的（第 4 節最後一列）。

（`docs/architecture/github-token-retirement.md` 原本的 C1「連續 3 個工作天沒有切回」與 C2「模擬器還原成功」，照使用者 11/20 的決定改成當天：C2 的「匯出全部資料」在 3.8 第 2 步做；模擬器還原要不要另外做是待決定。）

## 4. 退回方式

| 卡在哪裡 | 怎麼辦 | 會不會掉資料 |
|---|---|---|
| 凍結的 PR 還沒合併 | 不合併 | 不會 |
| 已凍結、還沒切換（匯入失敗、報告不同、確認畫面不對） | 先保持凍結處理那一個部門（按「再試一次」；內容相同的跳過、少的補上）。今天要放棄：revert 凍結的 PR（九個部門回 GitHub，公告恢復編輯）。已經匯入正式專案的部門資料留著；改天重來前照附錄 A.4.1 第 2 步在主控台清掉那些部門 | 不會：資料檔沒有被動過 |
| 切換的 PR 合併後、還沒有人在新資料庫改過 | revert 切換的 PR，再 revert 凍結的 PR（或一個 PR 把九行的 `source` 全部拿掉），等 1～2 分鐘 | 不會 |
| 已經有人在新資料庫改過，只有一兩個部門有問題 | 那幾個部門照附錄 A.4 單獨退回（撤這個部門的角色 → 匯出備份 → 一個 PR 把那幾行改回 github → 主控台檢查 `[0, 0]` → GitHub 模式匯入備份寫回）；其他部門留在新資料庫 | 不會；但切換後新記的會議紀錄（秘書處）不會寫回資料檔（匯出備份不含會議紀錄） |
| 全部都要退回 | 每個部門各做一次附錄 A.4：先在「人員」一次撤掉所有人的部門角色（總管理員除外）→ 逐部門匯出備份 → 一個 PR 九行全部改回 github → 逐部門檢查 `[0, 0]`、匯入備份 | 同上 |
| 權杖已經作廢之後才要退回 | 先照 T2 在 GitHub 發一把新權杖（你本人），用看板的「網站管理」換上，再照上面做。附錄 A.4 第 6 步的「匯入備份」要用舊身分＋密碼登入 GitHub 模式 | 不會，但多一步 |

所以**作廢權杖排在當天最後**（3.8 核對完、大家用了一段時間沒有問題之後）。

任何時候懷疑權杖外流：照 `github-token-retirement.md` 第 3 節的緊急程序，先作廢權杖。

## 5. 全部切完之後

- 作廢權杖的條件（`github-token-retirement.md` 第 2 節第三段 C1～C4）全部成立後，由你在 GitHub 上作廢。C2 的「匯出全部資料」：系統管理 → 匯出全部資料（存成一個 JSON，含角色、稽核紀錄，存到只有總管理員看得到的地方）。
- 作廢後要拆掉的舊程式清單：`docs/architecture/legacy-removal.md`。
- 舊資料檔留在 repo 當唯讀備份，不刪、不改。

## 附錄 A：一次一個部門的切換（2026-11-20 之前的做法）

九個部門同一天切換之後，這一段只在「一兩個部門要單獨退回或重來」時用。內容沒有改，只把節號改成 A.2～A.5。

## A.2 順序

1. **水果部**（測試部門，網址 `?d=fruit`）：完整走一次，包括附錄 A.4 的「回復」也實際做一次。
2. **一個自願的小部門**（資料少的：財務部、工務部、行銷部、公關部都幾乎是空的）。

## A.3 每個部門的切換（以水果部為例，其他部門把 `fruit`、`data-fruit.json` 換成那個部門的代號與檔名）

部門代號與資料檔：權益部 `rights`（`data.json`）、會長室 `president`、秘書處 `secretariat`、行銷部 `marketing`、財務部 `finance`、活動部 `events`、社務部 `affairs`、公關部 `pr`、工務部 `works`、水果部 `fruit`（其他部門的檔名都是 `data-代號.json`）。

### A. 凍結（暫停編輯）

1. 開 PR，只改 `dept/config.js` 裡這個部門那一行，在最後加上 `source: "frozen"`：
   ```js
   { id: "fruit",       name: "水果部", test: true, source: "frozen" },
   ```
2. 合併，等 1～2 分鐘，打開 `https://（網站）/index.html?d=fruit`，看到「這個部門正在搬到新資料庫，暫停編輯。」就是凍結成功。
3. 在部門群組公告：「○○部看板暫停編輯，約 30 分鐘」。

凍結只靠程式設定，不寫資料檔。凍結期間看板仍然看得到，只是不能存。

### B. 記下來源版本（之後比對、回復都靠它）

在 repo 資料夾：
```bash
git fetch origin main
git rev-parse origin/main                         # 這一串就是 commit SHA，抄下來
git show origin/main:data-fruit.json | sha256sum  # 資料檔的 SHA-256，抄下來
git tag pre-firestore-fruit-20261120 origin/main  # 日期換成今天
git push origin pre-firestore-fruit-20261120
```
（macOS 沒有 `sha256sum` 時用 `shasum -a 256`。）

### C. 備份

```bash
git show origin/main:data-fruit.json > ~/看板備份/data-fruit-切換前.json
```
這份就是切換前的完整內容（含雲端設定與密碼雜湊，不要貼到群組）。存到學生會公用帳號的雲端硬碟、只有幹部看得到的資料夾。

### D. 匯入

**正式匯入（網頁）**
1. 打開 `https://（網站）/index.html?d=fruit`（凍結中的部門；已切換的部門也可以）。
2. 右下「設定」→「用 Google 登入」，用總管理員的帳號。
3. 設定頁出現「系統管理」→ 點它 →「匯入」。
4. 清單每個部門旁邊標著「GitHub」「凍結中」「新資料庫」。點「水果部」（應該標「凍結中」）。
5. 跳出「匯入 水果部」，有兩格要填：**commit**（第 B 步抄的那一串 40 碼）與**資料檔的 SHA-256**（第 B 步抄的 64 碼）→ 按「確定」。標題後面多了「（還沒凍結）」或「（已切到新資料庫）」就先按取消，回第 A 步確認。
6. 畫面顯示「讀取並核對資料檔」。核對的是：那個 commit 的資料檔 SHA-256 等於你填的、而且 `main` 現在的同一個檔跟它一樣。任何一項不符就停在紅字（結尾都是「沒有寫入」），這時候沒有寫進任何東西：
   - 「SHA-256 跟輸入的不同」：回第 B 步重新確認抄的值（畫面只顯示讀到的開頭 12 碼，不要照畫面抄）。
   - 「這個 commit 之後資料檔又被改過」：凍結之後還有人存檔。回第 A 步確認凍結已經上線，再重做第 B、C 步。
   - 「這個 commit 沒有這個資料檔」：commit 抄錯了。
7. 核對通過會出現**確認畫面**（還沒寫入）：來源（檔名、repo、commit、SHA-256）、會寫入的筆數、**舊身分名單**（每個人的名字與「管理員／成員」）。
   - 名單要跟這個部門實際的幹部一樣；多出不認識的名字、或角色不對 → 按「返回」，不要匯入，看附錄 A.5。
   - 出現「格式不合、匯入時會清空的欄位」：資料檔裡有日期不是 `YYYY-MM-DD` 這類固定格式，匯入時那幾格會變成空白。正常的資料檔不會有這一段；有的話先截圖回報再決定要不要匯入。
   - 出現「超過規則的上限」：沒有「確認匯入」的按鈕，照列出來的項目先在看板上改好（卡片太長、舊身分的名字超過 60 字等），再從第 B 步重來。
8. 按「確認匯入」。畫面顯示「寫入 1/3…」「檢查」，然後出現報告（看第 E 步）。寫入的就是剛才核對過的那一份。

- 匯入讀的是 GitHub 上這個網站的 repo（`STUSTSA/council`）你填的那個 commit 的資料檔（只讀，不用權杖、不改資料檔）；報告上印出 `STUSTSA/council@main · commit …`，repo 不對就不要往下做。寫到哪個專案由 `dept/config.js` 的 `firebase` 決定，報告最上面那行就是專案 ID（正式專案是 `stustsa-council`；2026-11-20 之前的開發專案是 `stustsa-council-dev`）。
- 可以重按「再匯入一次」（會用同一組 commit 與 SHA-256 重新核對、再出現一次確認畫面）：內容相同的跳過、少的補上、被改過的列為衝突不覆寫，結果不變。
- 不是總管理員的人看不到「系統管理」；就算繞過畫面直接呼叫，也會被規則拒絕（`im1.js` 第 5 段）。

**先在模擬器用同一個版本演練**（建議每個部門切換前都做，確認資料檔在這個 commit 匯得進去）：
- 視窗一（開著不要關）：
  ```bash
  cd backend
  npm run emulators
  ```
- 視窗二：
  ```bash
  cd backend
  export FIRESTORE_EMULATOR_HOST=127.0.0.1:8080          # Windows PowerShell：$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"
  node migrate/cli.js --emulator --dept=fruit --commit=第B步的SHA
  echo $?                                                 # PowerShell：echo $LASTEXITCODE
  ```
`--commit` 讓它讀第 B 步那個版本的資料檔（用 `git show`，不碰工作資料夾裡的檔案）。

### E. 看筆數報告（什麼樣子算成功）

匯入完網頁上會出現一張表（命令列印出的是同一張），例如權益部：

```
項目                        資料檔  Firestore  結果
卡片（即時回報）                42         42  相同
版本（遷移產生的第 1 版）       42         42  相同
母議題                           4          4  相同
週報                            10         10  相同
標籤                             1          1  相同
時間標記                        15         15  相同
議題註記                        11         11  相同
舊身分                           2          2  相同
多行說明（逐字還原）            20         20  相同
通過 V1 …
通過 V2 …
通過 V3 …
通過 V4 …
通過 V6 …
結果：通過（每一列相同、V1～V4、V6 都通過）
```

**成功＝每一列都是「相同」、V1～V4、V6 都是「通過」（沒有 V5 是正常的：V5＝重跑一次，看「再匯入一次」寫入 0、衝突 0）、最後是「結果：通過」，下面一行「衝突 0」**（命令列：`echo $?` 印出 `0`）。

- 「指到還沒匯入的部門 N 筆」：正常（例如會長室追蹤了權益部的議題，而權益部還沒切）。等那個部門匯入後就指得到。
- 「超過上限的卡片 N 張」（03 審查）：表格上面會先列出超過規則上限的卡片（超過 50 行、一行超過 1000 字、超過 10 個超連結、超連結顏色不是 `#rrggbb`、名稱超過 500 字）。有這一段時匯入會**在寫入任何文件之前就停下**（不會寫到一半），`--dry-run` 也會列出並以結束碼 1 結束：請部門的人先在看板（GitHub 模式）把那幾張改短，再從 B 步重來。
- 任何一列是「不同」（紅字）、任何一項是「失敗」、「結果：不通過」、衝突不是 0、或 `echo $?` 不是 0 → **不要往下做**，看附錄 A.5。
- 想再看一次報告：網頁按「再匯入一次」（不會重複寫，報告重算）；命令列 `node migrate/cli.js --emulator --dept=fruit --report --commit=第B步的SHA`。報告只在開放編輯前有意義（開始編輯後數量本來就會變）。

### F. 部門的人加入

4. 系統管理 → 人員：確認每個人都在、角色正確。

### G. 切換

1. 開 PR，把第 A 步加的 `source: "frozen"` 改成 `source: "firestore"`：

2. 合併，等 1～2 分鐘。

## A.4 回復（水果部要實際演練一次）

切換後發現問題、要退回 GitHub。**順序不能換**：先讓新資料庫不能再寫，才匯出；不然匯出之後還有人（或還開著舊設定的分頁）在新資料庫存東西，那些修改不會進備份，改回 GitHub 後就找不到了。

1. **公告暫停編輯**（群組）。
2. **總管理員撤銷這個部門的角色**：系統管理 → 人員 → 點每一位有「水果部」角色的人 → 水果部那一列按「撤銷」（只撤這個部門，其他部門的角色不動）。撤銷立刻生效：規則每次寫入都重新讀角色，他們的分頁（包括還開著、沒重新整理的）按儲存都會被擋下（`fw1.js` 第 5 段驗證過）。記下每個人原本的角色（之後重新切換時要還給他們）。**總管理員自己在第 3～5 步之間不要在水果部的看板改任何東西。**
3. **匯出**：總管理員在 `firestore` 模式的水果部看板 → 設定 → 備份 → 匯出備份，存下 JSON 檔。**記下匯出的時間**（例如 `2026-11-20 14:30`）。這份就是切換後的最新內容（不含雲端設定、權杖、密碼、會議紀錄；寫回時沿用 GitHub 上原本的）。
4. 開 PR，把這個部門的 `source: "firestore"` 拿掉（或改成 `source: "github"`），合併，等 1～2 分鐘。
5. **確認匯出之後新資料庫沒有新的修改**：總管理員在同一個瀏覽器（之前用 Google 登入過的）打開 `?d=fruit` → 按 F12 開「主控台」（Console），貼上這三行（把時間換成第 3 步記下的；只印數字，不會顯示任何內容或機密），按 Enter：
   ```js
   const F = await storeFsGet(), since = Date.parse("2026-11-20T14:30:00+08:00");
   [(await F.versionsSince(CFG.firebase, "fruit", since)).length,
    (await F.auditSince(CFG.firebase, since)).filter(a => fsAuditDept(a) === "fruit").length]
   ```
   顯示 `[0, 0]`＝匯出之後沒有任何卡片的新版本、部門設定的修改、卡片刪除，可以繼續。不是 `[0, 0]`：有人在匯出之後寫入（通常是第 2 步漏撤了誰）→ 回到第 2 步把人撤乾淨，再從第 3 步重新匯出（第 4 步已合併就不用再合併）。議題、週報、標籤沒有版本歷史，這個檢查看不到；第 2 步撤完角色後只有總管理員能寫它們，所以第 3～5 步總管理員不要改看板。
6. 在看板（現在讀 GitHub 了）用原本的方式登入（舊身分＋密碼）→ 設定 → 備份 → 匯入備份 → 選第 3 步的檔案 → 確定。看到「已匯入並儲存」＝已經寫回 GitHub 的資料檔（會多一筆 commit，編輯紀錄看得到）。
7. 對照：看板內容＝切換前的內容＋切換後新增或修改的東西。公告恢復編輯（在 GitHub 模式）。
8. **角色先不要還回去**：水果部現在讀寫 GitHub，Google 角色用不到；還回去的話，還開著舊設定的分頁又能寫進新資料庫（之後沒人看）。等「再切換一次」時才還（下面附錄 A.4.1）。

演練結果（模擬器，`sw1.js` B 段）：用一份內容最多的部門（權益部複本：成員的密碼與權杖欄位、共用密碼、會議紀錄、卡片、時間標記、議題註記）和水果部各跑一次：撤銷角色後編輯者寫不進去、第 5 步的檢查是 `[0, 0]`、寫回的內容＝切換前的資料檔＋在新資料庫做的修改；雲端設定、權杖、共用密碼、成員的密碼與權杖、會議紀錄沿用原本的（只比雜湊，不印出來）。

### A.4.1 回復之後再切換一次

新資料庫裡還留著這個部門上一次的資料（含切換後的修改）。匯入程式只會「新增、內容相同就跳過、不同就列成衝突」，**不會刪掉多出來的東西**：上次之後在 GitHub 刪掉的卡片會在新資料庫復活，改過的卡片會變成衝突。所以再切換之前，要先把這個部門在新資料庫的資料清掉：

1. 照附錄 A.3 的 A～C（凍結、記 SHA、備份）。
2. **清掉這個部門在新資料庫的看板資料**（總管理員）：
   - 匯入頁沒有「回復這一批」與「清空這個部門」（02D D-a 只做了匯入；待辦，`docs/architecture/README.md`「02D 新增的待辦」）。命令列的 `rollbackImport` 只連模擬器。
   - 在 Firebase 主控台（由你操作）刪掉 `deptId` 是這個部門的 `cards`（刪除時勾選「一併刪除子集合」，連同 `versions`）、`events`、`issues`、`weeks`、`labels`，以及 `deptSettings/fruit`。**不要刪** `legacyIdentities`（舊身分的認領）、`roles`、`auditLogs`、`departments/fruit`。刪完在主控台用篩選 `deptId == fruit` 確認上面五個集合都是 0 份（命令列只連模擬器，不能用來查正式專案）。
3. 從附錄 A.3 的 D（匯入）繼續做完；第 F 步把附錄 A.4 第 2 步撤掉的角色還給原本的人（系統管理 → 人員 → 改角色，或重新發 QR）。

## A.5 出問題時

| 卡在哪一步 | 怎麼辦 | 會不會掉資料 |
|---|---|---|
| A 凍結 PR 還沒合併 | 不合併就好 | 不會 |
| A～C（已凍結，還沒匯入） | revert 凍結的 PR（`source` 回到預設的 github），公告恢復編輯 | 不會：資料檔沒有被動過 |
| D 匯入中途失敗（畫面顯示「失敗（…）」或「讀不到資料檔」） | 保持凍結，按「再試一次」：已寫進去的內容相同會跳過、只補上沒寫的（文件 ID 固定，不會重複）。還是失敗：把錯誤文字給我。網頁還沒有「回復這一批」（命令列的 `rollbackImport` 只連模擬器；待辦），不想今天處理就 revert 凍結的 PR：留下的部分資料沒有人看得到編輯入口，下次匯入時相同的跳過、不同的列成衝突 | 不會：凍結期間沒有人寫 |
| E 報告有「不同」或「失敗」 | 保持凍結，不要發 QR。把報告整段複製給我（報告只有數量與文件代號，沒有機密）。要恢復編輯就 revert 凍結的 PR | 不會 |
| F 有人加入不了 | 保持凍結，重新產生 QR（舊的自動失效）；LINE 裡打開的改用瀏覽器。今天加不完：revert 凍結的 PR，改天從 F 繼續（已匯入的資料留著，內容相同的不會重寫） | 不會 |
| G 合併後看板打不開或讀不到 | 還沒有人在新資料庫編輯：revert 切換的 PR 和凍結的 PR，回到 GitHub | 不會：資料檔沒有被動過 |
| H 已經有人在新資料庫改過東西才發現問題 | 照附錄 A.4：先撤銷這個部門的角色 → 匯出 → 改回 GitHub → 確認匯出後沒有新修改 → 匯入備份寫回 | 不會（03 上線前結構能一對一對回去）；漏撤角色、匯出後還有人存的修改會被第 5 步的檢查抓到 |
| 回復之後要再切換 | 照附錄 A.4.1：先清掉這個部門在新資料庫的資料，再從 D 重新匯入 | 不會：資料檔是最新的；不清掉的話上次的舊卡片會復活 |
| 權杖已經作廢之後想回到 GitHub | 要先再發一把新權杖（T2 的做法），才能寫回 GitHub | 不會，但要多一步 |

任何時候懷疑權杖外流：照 `github-token-retirement.md` 第 3 節的緊急程序，先作廢權杖。
