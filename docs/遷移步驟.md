## 1. 事前準備（全部部門只做一次）

1. **權杖保險（T1～T5）**：照 `docs/architecture/github-token-retirement.md` 第 2 節第一段做。重點：權杖是 fine-grained、只授權這個 repo、只有 Contents 讀寫；到期日設在「預計最後一個部門切換日＋14 天」。這些都在 GitHub 網頁上由你操作，我不經手權杖。
2. **部署規則與索引**（要你同意才做；只影響指定的專案）：在 `backend/` 資料夾
   ```bash
   npx firebase login
   npx firebase deploy --only firestore:rules,firestore:indexes --project 專案ID
   ```
   先對開發專案 `stustsa-council-dev` 做，確認沒問題再對正式專案做。CLI 問要不要刪掉檔案裡沒有的索引時，回答「不要」（No）。
3. **確認任何 Google 帳號都能登入**：照 `docs/architecture/verification.md` 第 9.2 節在主控台看 OAuth 同意畫面（使用者類型「外部」、發布狀態「正式版」）。
4. **第一位總管理員**：照 `docs/architecture/invitations-roles-audit.md` 第 7 節。要當總管理員的人先在看板用 Google 登入一次（拿到 UID），再由公用帳號在 Firebase 主控台手動建 `roles/{UID}` 與 `auditLogs/roles_{UID}_1` 兩份文件（內容照那一節，一個字都不要改）。
5. **部門文件 `departments`**：每個部門匯入時會一起建立自己的那一份，不用另外做。QR 邀請要求部門文件存在，所以「發 QR」一定排在「匯入」之後（第 3 步的順序已經是這樣）。
6. **換成正式專案的網頁設定**：開一個 PR，把 `dept/config.js` 裡 `firebase: { ... }` 換成正式專案的 apiKey、authDomain、projectId、appId（這些不是機密）。這個 PR 跟任何一個部門的切換分開合併。
7. **在你的電腦演練一次**（只用模擬器，不碰任何真的專案、不改資料檔）。第一次要先在 `backend/` 執行 `npm install`，電腦要有 Node.js 與 Java。
   ```bash
   cd backend
   npx firebase emulators:exec --only firestore,auth --project demo-stustsa-board "node ../tools/tests/sw1.js"
   ```
   最後一行是「全部通過（62 項）」就是成功（約 1 分鐘）。它會先把資料檔複製到暫存資料夾，只讀複本。

## 3. 每個部門的切換（以水果部為例，其他部門把 `fruit`、`data-fruit.json` 換成那個部門的代號與檔名）

部門代號與資料檔：權益部 `rights`（`data.json`）、會長室 `president`、秘書處 `secretariat`、行銷部 `marketing`、財務部 `finance`、活動部 `events`、社務部 `affairs`、公關部 `pr`、工務部 `works`、水果部 `fruit`（其他部門的檔名都是 `data-代號.json`）。

### A. 凍結（暫停編輯）

1. 開 PR，只改 `dept/config.js` 裡這個部門那一行，在最後加上 `source: "frozen"`：
   ```js
   { id: "fruit",       name: "水果部", test: true, source: "frozen" },
   ```
2. 合併，等 1～2 分鐘，打開 `https://（網站）/index.html?d=fruit`，看到「這個部門正在搬到新資料庫，暫停編輯。」就是凍結成功。
3. 在部門群組公告：「○○部看板暫停編輯，約 30 分鐘」。

凍結只靠程式設定，不寫資料檔。凍結期間看板仍然看得到，只是不能存。

### B. 記下來源版本（之後比對、回復都靠它）

在 repo 資料夾：
```bash
git fetch origin main
git rev-parse origin/main                         # 這一串就是 commit SHA，抄下來
git show origin/main:data-fruit.json | sha256sum  # 資料檔的 SHA-256，抄下來
git tag pre-firestore-fruit-20261120 origin/main  # 日期換成今天
git push origin pre-firestore-fruit-20261120
```
（macOS 沒有 `sha256sum` 時用 `shasum -a 256`。）

### C. 備份

```bash
git show origin/main:data-fruit.json > ~/看板備份/data-fruit-切換前.json
```
這份就是切換前的完整內容（含雲端設定與密碼雜湊，不要貼到群組）。存到學生會公用帳號的雲端硬碟、只有幹部看得到的資料夾。

### D. 匯入

- **正式專案**：總管理員登入後在瀏覽器執行匯入頁 — **還沒做（第 0 節）**。做好之後，這裡會寫成「打開哪個網址、按哪個鍵」。
- **先在模擬器用同一個版本演練**（建議每個部門切換前都做，確認資料檔在這個 commit 匯得進去）：
  - 視窗一（開著不要關）：
    ```bash
    cd backend
    npm run emulators
    ```
  - 視窗二：
    ```bash
    cd backend
    export FIRESTORE_EMULATOR_HOST=127.0.0.1:8080          # Windows PowerShell：$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8080"
    node migrate/cli.js --emulator --dept=fruit --commit=第B步的SHA
    echo $?                                                 # PowerShell：echo $LASTEXITCODE
    ```
  `--commit` 讓它讀第 B 步那個版本的資料檔（用 `git show`，不碰工作資料夾裡的檔案）。

### E. 看筆數報告（什麼樣子算成功）

匯入完會印出一張表，例如權益部：

```
項目                        資料檔  Firestore  結果
卡片（即時回報）                42         42  相同
版本（遷移產生的第 1 版）       42         42  相同
母議題                           4          4  相同
週報                            10         10  相同
標籤                             1          1  相同
時間標記                        15         15  相同
議題註記                        11         11  相同
舊身分                           2          2  相同
多行說明（逐字還原）            20         20  相同
通過 V1 …
通過 V2 …
通過 V3 …
通過 V4 …
通過 V6 …
結果：通過（每一列相同、V1～V6 都通過）
```

**成功＝每一列都是「相同」、V1～V6 都是「通過」、最後一行是「結果：通過」、`echo $?` 印出 `0`。**

- 「指到還沒匯入的部門 N 筆」：正常（例如會長室追蹤了權益部的議題，而權益部還沒切）。等那個部門匯入後就指得到。
- 任何一列是「不同」、任何一項是「失敗」、或 `echo $?` 不是 0 → **不要往下做**，看第 5 節。
- 想再看一次報告（不重新匯入）：`node migrate/cli.js --emulator --dept=fruit --report --commit=第B步的SHA`。報告只在開放編輯前有意義（開始編輯後數量本來就會變）。

### F. 部門的人加入

1. 總管理員在看板（任何一個已切換的部門，或用水果部）→ 設定 → 會長室管理 → QR 邀請 → 選部門、角色（編輯者／管理員）→ 產生。
2. 部門的人用手機相機掃（不要用 LINE 掃；LINE 會要求改用瀏覽器開）→ 用 Google 登入 →「加入」。QR 10 分鐘內有效、只能用一次；人多就按「重新產生」。
3. 舊身分：產生 QR 時在「舊身分」欄選他原本的身分（例如「權益部・小芸」），加入後卡片上的負責人名字就接到他的帳號。
4. 會長室管理 → 人員：確認每個人都在、角色正確。

### G. 切換

1. 開 PR，把第 A 步加的 `source: "frozen"` 改成 `source: "firestore"`：
   ```js
   { id: "fruit",       name: "水果部", test: true, source: "firestore" },
   ```
2. 合併，等 1～2 分鐘。

### H. 確認能編輯

請一位部門編輯者：
1. 打開 `?d=fruit` → 設定 → 用 Google 登入。設定頁顯示他的名字與「水果部編輯者」。
2. 看板上的卡片、議題、週報跟切換前一樣（拿第 C 步的備份對照幾張）。
3. 新增一張卡片 → 儲存 → 重新整理，卡片還在。
4. 設定 → 編輯紀錄：看得到剛剛那一筆（「即時回報｜新增｜卡片名稱」）。
5. 打開一個還沒切換的部門（例如 `?d=finance`）：照常、可以存檔。

全部正常 → 在群組公告恢復編輯。

## 4. 回復（水果部要實際演練一次）

切換後發現問題、要退回 GitHub。**順序不能換**：先讓新資料庫不能再寫，才匯出；不然匯出之後還有人（或還開著舊設定的分頁）在新資料庫存東西，那些修改不會進備份，改回 GitHub 後就找不到了。

1. **公告暫停編輯**（群組）。
2. **總管理員撤銷這個部門的角色**：會長室管理 → 人員 → 點每一位有「水果部」角色的人 → 水果部那一列按「撤銷」（只撤這個部門，其他部門的角色不動）。撤銷立刻生效：規則每次寫入都重新讀角色，他們的分頁（包括還開著、沒重新整理的）按儲存都會被擋下（`fw1.js` 第 5 段驗證過）。記下每個人原本的角色（之後重新切換時要還給他們）。**總管理員自己在第 3～5 步之間不要在水果部的看板改任何東西。**
3. **匯出**：總管理員在 `firestore` 模式的水果部看板 → 設定 → 備份 → 匯出備份，存下 JSON 檔。**記下匯出的時間**（例如 `2026-11-20 14:30`）。這份就是切換後的最新內容（不含雲端設定、權杖、密碼、會議紀錄；寫回時沿用 GitHub 上原本的）。
4. 開 PR，把這個部門的 `source: "firestore"` 拿掉（或改成 `source: "github"`），合併，等 1～2 分鐘。
5. **確認匯出之後新資料庫沒有新的修改**：總管理員在同一個瀏覽器（之前用 Google 登入過的）打開 `?d=fruit` → 按 F12 開「主控台」（Console），貼上這三行（把時間換成第 3 步記下的；只印數字，不會顯示任何內容或機密），按 Enter：
   ```js
   const F = await storeFsGet(), since = Date.parse("2026-11-20T14:30:00+08:00");
   [(await F.versionsSince(CFG.firebase, "fruit", since)).length,
    (await F.auditSince(CFG.firebase, since)).filter(a => fsAuditDept(a) === "fruit").length]
   ```
   顯示 `[0, 0]`＝匯出之後沒有任何卡片的新版本、部門設定的修改、卡片刪除，可以繼續。不是 `[0, 0]`：有人在匯出之後寫入（通常是第 2 步漏撤了誰）→ 回到第 2 步把人撤乾淨，再從第 3 步重新匯出（第 4 步已合併就不用再合併）。議題、週報、標籤沒有版本歷史，這個檢查看不到；第 2 步撤完角色後只有總管理員能寫它們，所以第 3～5 步總管理員不要改看板。
6. 在看板（現在讀 GitHub 了）用原本的方式登入（舊身分＋密碼）→ 設定 → 備份 → 匯入備份 → 選第 3 步的檔案 → 確定。看到「已匯入並儲存」＝已經寫回 GitHub 的資料檔（會多一筆 commit，編輯紀錄看得到）。
7. 對照：看板內容＝切換前的內容＋切換後新增或修改的東西。公告恢復編輯（在 GitHub 模式）。
8. **角色先不要還回去**：水果部現在讀寫 GitHub，Google 角色用不到；還回去的話，還開著舊設定的分頁又能寫進新資料庫（之後沒人看）。等「再切換一次」時才還（下面第 4.1 節）。

演練結果（模擬器，`sw1.js` B 段）：用一份內容最多的部門（權益部複本：成員的密碼與權杖欄位、共用密碼、會議紀錄、卡片、時間標記、議題註記）和水果部各跑一次：撤銷角色後編輯者寫不進去、第 5 步的檢查是 `[0, 0]`、寫回的內容＝切換前的資料檔＋在新資料庫做的修改；雲端設定、權杖、共用密碼、成員的密碼與權杖、會議紀錄沿用原本的（只比雜湊，不印出來）。

### 4.1 回復之後再切換一次

新資料庫裡還留著這個部門上一次的資料（含切換後的修改）。匯入程式只會「新增、內容相同就跳過、不同就列成衝突」，**不會刪掉多出來的東西**：上次之後在 GitHub 刪掉的卡片會在新資料庫復活，改過的卡片會變成衝突。所以再切換之前，要先把這個部門在新資料庫的資料清掉：

1. 照第 3 節 A～C（凍結、記 SHA、備份）。
2. **清掉這個部門在新資料庫的看板資料**（總管理員）：
   - 只有匯入、之後完全沒人改過的情況：用匯入頁的「回復這一批」（`backend/migrate/run.js` 的 `rollbackImport`，只刪那一批匯入**而且沒被改過**的文件）。切換後有人改過就不夠用（改過的會留下）。
   - 一般情況：在 Firebase 主控台（由你操作）刪掉 `deptId` 是這個部門的 `cards`（刪除時勾選「一併刪除子集合」，連同 `versions`）、`events`、`issues`、`weeks`、`labels`，以及 `deptSettings/fruit`。**不要刪** `legacyIdentities`（舊身分的認領）、`roles`、`auditLogs`、`departments/fruit`。刪完在主控台用篩選 `deptId == fruit` 確認上面五個集合都是 0 份（命令列只連模擬器，不能用來查正式專案）。
   - 正式匯入頁還沒做；做的時候要一起提供「清空這個部門」（待辦，`docs/architecture/README.md`「02D 新增的待辦」），之後就不用在主控台手動刪。
3. 從第 3 節 D（匯入）繼續做完；第 F 步把第 4 節第 2 步撤掉的角色還給原本的人（會長室管理 → 人員 → 改角色，或重新發 QR）。

## 5. 出問題時

| 卡在哪一步 | 怎麼辦 | 會不會掉資料 |
|---|---|---|
| A 凍結 PR 還沒合併 | 不合併就好 | 不會 |
| A～C（已凍結，還沒匯入） | revert 凍結的 PR（`source` 回到預設的 github），公告恢復編輯 | 不會：資料檔沒有被動過 |
| D 匯入中途失敗 | 保持凍結。正式專案：匯入頁要一起提供「回復這一批」（程式已經有，`backend/migrate/run.js` 的 `rollbackImport`：批次改成 `rollingBack`，只刪這一批匯入而且沒被改過的資料，見 `migration.md` 第 7 節），修好後用新的批次號重新匯入（文件 ID 固定，不會重複）。模擬器：關掉視窗一重開就是空的，再跑一次。不想今天處理：revert 凍結的 PR | 不會：凍結期間沒有人寫 |
| E 報告有「不同」或「失敗」 | 保持凍結，不要發 QR。把報告整段複製給我（報告只有數量與文件代號，沒有機密）。要恢復編輯就 revert 凍結的 PR | 不會 |
| F 有人加入不了 | 保持凍結，重新產生 QR（舊的自動失效）；LINE 裡打開的改用瀏覽器。今天加不完：revert 凍結的 PR，改天從 F 繼續（已匯入的資料留著，內容相同的不會重寫） | 不會 |
| G 合併後看板打不開或讀不到 | 還沒有人在新資料庫編輯：revert 切換的 PR 和凍結的 PR，回到 GitHub | 不會：資料檔沒有被動過 |
| H 已經有人在新資料庫改過東西才發現問題 | 照第 4 節：先撤銷這個部門的角色 → 匯出 → 改回 GitHub → 確認匯出後沒有新修改 → 匯入備份寫回 | 不會（03 上線前結構能一對一對回去）；漏撤角色、匯出後還有人存的修改會被第 5 步的檢查抓到 |
| 回復之後要再切換 | 照第 4.1 節：先清掉這個部門在新資料庫的資料，再從 D 重新匯入 | 不會：資料檔是最新的；不清掉的話上次的舊卡片會復活 |
| 權杖已經作廢之後想回到 GitHub | 要先再發一把新權杖（T2 的做法），才能寫回 GitHub | 不會，但要多一步 |

任何時候懷疑權杖外流：照 `github-token-retirement.md` 第 3 節的緊急程序，先作廢權杖。
