# Firestore 讀取量（2026-11-23）

Spark 每日讀取 5 萬、寫入 2 萬（台灣時間 16:00 重置）。下面用 **C＝該部門卡片數、D＝議題＋週報＋標籤＋事件＋舊身分文件數** 估算（一次進部門 ≈ 2 ＋ C ＋ D 份）；實際數字請在登入後的 console 執行 `BoardFirestore.stats.docs`（這個分頁到目前讀了幾份）。以一個部門 C＋D＝150 份為例（九個部門合計約 1,350）。

| 情境 | 改前 | 改後（期限內） | 改後（過期或剛寫入） |
|---|---|---|---|
| 一般幹部重新整理一次看板 | 2＋150＋2（ensureUser）＋1（角色）≈ 155 | 角色 1（持久化快取後多半只算變動） | 同改前 |
| 進部門→返回首頁→再進同一部門（首頁換頁等於整頁重載） | 每進一次 ≈ 155 | 第一次 155，之後 ≈ 1 | 同改前 |
| 會長室開「追蹤」或秘書處開「會議」（讀其他九部門） | ≈ 1,350 每次，之後 5 分鐘記憶體內不重讀、重新整理就重讀 | 第一次 1,350，10 分鐘內重新整理／再進 ≈ 0 | 1,350 |
| 會長室「編輯量」（24 小時版本歷史、九部門） | 每次 ＝當天編輯次數合計，重新整理就重讀 | 5 分鐘內 ≈ 0 | 同改前 |
| 打開人員／帳號頁（全部使用者的名稱） | 使用者數 N 每次 | 10 分鐘內 0 | N |
| 儲存一次修改 | 寫入＋強制重讀整個部門 ≈ 155 | 不變（刻意，衝突檢查必須讀最新） | 同 |
| 行事曆「活動／會議」按月 | 每次進／換月都查 | 同一個月 10 分鐘內 0 | 同改前 |

要點：DievE 反覆測試「重開頁、進出部門」這類操作，改前每次都是整個部門，改後除了第一次幾乎為 0；最大來源是「會長室／秘書處讀九部門」（單次最高），其次是每次進看板的整部門重讀。

## 還能再省（要先決定／需要規則配合，這次沒做）
1. **增量同步**：`updatedAt > 上次` 只讀變動的文件，需要所有文件都有可靠的 `updatedAt` 與刪除標記（現在卡片是真的刪除），並且索引要加。可把「過期後的重讀」從 C＋D 降到只有變動的幾份。
2. **完成紀錄分頁載入**：完成的卡片會一直累積，`loadDept` 目前讀全部 `open`／`done`；改成只讀近幾週的 `done`，舊的按「載入更多」。要改畫面與 `state` 結構，先問。
3. **首頁／追蹤摘要文件**（每部門一份「卡片數、最新動態」）：會長室追蹤與首頁不必讀整個部門，需要新增文件與規則。
4. 快取有效期若還是太貪心可調整：`store-firestore.js` 最上方的 `TTL_*`。
